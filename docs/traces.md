# Traces architecture and rollout

## Vertical slice

An agent command hook emits its native JSON to `scripts/submit-hook.ts`. The bridge adds source, event ID, session ID, event name and receipt time; it never edits the native payload. `POST /api/events` validates the envelope and stores raw JSON plus a tool-name/event-name search projection in D1. `GET /api/events?q=<session-id-or-tool>` and stateless MCP `search_traces` return recent matching records (100 maximum). `GET /api/search?q=<words>` and MCP `search_trace_contents` search the payload contents instead (see below). Repeating an event ID for the same owner is idempotent; the first payload wins. The remote MCP endpoint is `POST /mcp` **on the API Worker URL**, not the Website URL.

All private routes reject requests without a Cloudflare Access identity, including direct workers.dev access. The single-tenant Access application permits the configured owner's email and, optionally, an explicitly provisioned Access service token. The API Worker is enrolled with Access and advertises managed OAuth with dynamic client registration for browser-based MCP clients. A hook is noninteractive: give it only a dedicated Access service token (ID + secret) via its local environment, never a browser session or a secret in a repository. The hook bridge fails open from the agent's perspective; delivery is best effort. No payload contents or credentials are logged intentionally. The Website is a public information page; its service-binding `/api/*` forwarding does **not** establish Access identity, so private API calls should use the API Worker URL directly.

Before any deployment, set `TRACES_ACCESS_EMAIL` to the account allowed to inspect traces. Without it, the Access policy matches an invalid placeholder email and intentionally admits nobody. Provision a Cloudflare Access service token and pass its **token ID** as `TRACES_ACCESS_SERVICE_TOKEN_ID` during the Alchemy plan if noninteractive submissions are wanted; this is a policy change requiring explicit approval. Keep the token _secret_ only on the local agent machine as `CF_ACCESS_CLIENT_SECRET`. `TRACES_ENDPOINT` is the API Worker base URL and `CF_ACCESS_CLIENT_ID` is the Access client ID. Set those three environment variables outside source control and run `bun scripts/submit-hook.ts claude-code` (or `codex`) as a command hook. Run a new agent session after editing hook settings. This is an opt-in bridge, not a production installer.

Public `GET /install` on the Website serves Markdown instructions with the API Worker's own URL, client-specific MCP registration commands, and opt-in hook examples. Authenticated MCP `inspect_hooks` returns the same text. A remote server cannot inspect or edit a caller's filesystem on its own. A future installer must run in the agent's local context, read and merge existing hook config (never overwrite), show the exact diff, request user approval, write atomically, and verify a test event. It must avoid printing or embedding secrets. Do not claim the current read-only tool has installed hooks.

## Storage and risk

D1 is the interactive session index and raw event store for this first slice. `/api/events` search is by exact session ID or escaped substring of projected tool/event names. Full-text search over payloads uses Cloudflare AI Search, described next. Source-specific mapping currently extracts `tool_name` or `toolName`, falling back to the event name; the complete source JSON remains in `raw` for later reinterpretation. Other agent event shapes need sample fixtures before richer mapping. A stored row that no longer decodes, such as one with malformed raw JSON or a retired source, is skipped in search results and logged by event ID only. Its raw column stays in D1 for a later migration. D1 failures return `503` on HTTP routes and JSON-RPC error `-32603` from MCP. Malformed JSON bodies return `400`.

## Content search

[Cloudflare AI Search](https://developers.cloudflare.com/ai-search/) holds a derived, plain-text copy of each trace; D1 stays the source of truth. `searchText` in `src/traces.ts` renders the envelope plus one `path: value` line per scalar in the raw payload, with strings unescaped, so prompts, commands and tool output read as written. The instance (`src/platform/cloudflare/search.ts`) uses built-in storage, so the Worker uploads each document through the Items binding and it is indexed immediately rather than on a sync schedule. It is keyword-only (BM25, no embeddings) with the trigram tokenizer: every whitespace-separated query term must appear, terms match substrings case-insensitively, and terms shorter than three characters may not match. Results are best match first, at most 20 events. Keyword queries bill as full-text queries.

Each document is named by a SHA-256 digest of `(owner, event ID)` and carries `owner` and `event_id` metadata. Uploads upsert by name, so re-indexing is idempotent. Search filters by `owner` in AI Search and then reads hits back from D1 through the owner's scope, so another owner's event can never be returned even if the index misbehaved. Hits whose `event_id` is missing or doesn't match a stored event are dropped. AI Search filters only the first 64 bytes of a string, which is another reason the D1 read re-checks ownership.

`POST /api/events` succeeds once D1 stores the event. It then uploads the document and sets `events.indexed_at` (migration `0002`). If the upload fails, the submission still succeeds, a warning is logged with the operation only, and the row stays unindexed. A cron trigger runs every minute and indexes up to 25 unindexed rows, newest first, four at a time. That sweep also backfills events stored before content search existed. Overlapping or repeated sweeps are safe because uploads upsert. A row that no longer decodes stays unindexed and is logged by event ID on each sweep that reaches it. A duplicate submission is never uploaded, so the first payload wins in the index too. Content search failures return `503` (`Trace content search unavailable`) and JSON-RPC `-32603`; ingestion and `/api/events` keep working during an AI Search outage.

Alchemy 2.0.0-beta.81 cannot declare a built-in-storage instance, so `patches/alchemy@2.0.0-beta.81.patch` adds `type: "builtin"`; see `patches/README.md`. AI Search has no local emulation, so `mise run dev` creates a real instance for the dev stage. Deleting a trace from D1 does not yet delete its document; retention work must cover both stores.

## Telemetry

Both Workers send Workers Observability logs and traces, sampling every request at prototype volume. Lower both rates together in `src/platform/cloudflare/api.ts` once traffic grows. On the API Worker, `Cloudflare.Telemetry` mirrors Effect spans into the Cloudflare trace waterfall. Each request gets an `Api.request` server span with method, path, matched route and status. Operations nest under it as `Traces.*`, `TraceStore.*`, `TraceIndex.*`, `Mcp.*`, `Identity.owner` and `Install.read`. The cron sweep is its own root span, `Traces.indexPending`, with indexed and failed counts. Spans and logs never carry search queries, session IDs, event IDs (except when a stored row fails to decode), headers or payloads. `src/api.test.ts` enforces this for spans. D1 row size, write throughput, retention/deletion, secret redaction, pagination, tenant separation, and Access OAuth client interoperability need evaluation before real traces containing sensitive prompts are accepted.

[Cloudflare Basin/Pipelines](https://developers.cloudflare.com/basin/) is GA and supports Worker/HTTP stream ingestion into Iceberg and SQL query. Ingestion-to-query can take minutes, so it is an **analytics/archive candidate**, not the interactive index. Evaluate pricing, size limits and propagation latency against production volume before adding a fan-out. No Basin resources or paid deployment have been created.
